# memory-egemma の規模試験：50〜5,000 セッション（LongMemEval-S）

対象: `dsh-plugins/packages/memory-egemma`（ブランチ dsh-plugin）。パッケージの `lib/`（ビルド済み）をそのまま使い、何も変更していない。
実ベクトルの測定は HEAD e550161（capture の窓の修正 790e13f を含む）、2026-10-24 05:48〜06:30。
機械: Apple M5 Max / 64 GiB、macOS 27.0.1、Node v22.23.1。EmbeddingGemma 300m は自前の egemma-server（:8296、fp32、終了時に停止済み）。
GPU 段は、C1 の終了印（`holdout2.log` の "holdout v2 done"、05:46）が出て、8091/8298 が閉じたのを確かめてから実行した。

## 結論

1. **速さと大きさは 5,000 セッション（5.2 万メッセージ）では問題にならない。**
   1 回の想起は p50 209 ms / p95 223 ms（クエリ埋め込み 16 ms を含む）、RSS 1.45 GB（ピーク 1.57 GB）、DB 339 MB、
   起動から最初の想起まで 0.75〜0.97 秒。基準（1 回 1 秒、RSS 2 GB）はどちらも越えない。
2. **ただし全部が保存メッセージ数に比例して増え、RSS が先に限界に来る。** 現状のコードでは RSS 2 GB に約 7,000〜8,000 セッション
   （7〜8 万メッセージ）で届く。10,000 セッション（合成ベクトルで実測）では RSS 2.8 GB（ピーク 3.1 GB）、想起 p50 384 ms / p95 404 ms、
   起動から最初の想起まで 2.4 秒。1 回 1 秒には約 2 万セッション以上で届く。
3. **時間もメモリも、ベクトル計算ではなく後処理で使われている。** 5,000 セッションの想起 193 ms（クエリ埋め込みを除く）のうち 65 % は
   「保存済みの全メッセージを毎回 clip する」処理で、10 % は全ユニットの並べ直し。cosine と並べ替えは 24 %。RSS の大半は、
   この毎回のゴミによる GC の余白。
4. **最小の修正（パッケージの外で試作。100 問すべて同じ結果）で、5,000 セッションの想起は 209 → 38 ms、RSS は 1.45 → 0.44 GB になる。**
   10,000 セッションでも 47 ms / 0.99 GB。近似索引（ANN）は当面いらない。int8 で減るのはメモリだけ（1/4）で、精度はほぼ同じ（下記）。
5. **規模で大きく落ちるのは精度。** 答えの発言が想起に入る割合は、50 セッションで 0.883、500 で 0.717、2,000 で 0.667、5,000 で
   0.517（60 問、5,000 − 50 = −0.367、95 % 区間 [−0.483, −0.250]）。50 で取れて 5,000 で落ちた問題は 22、逆は 0。
   根拠が古いか新しいかでは変わらない（3 つの古さで完全に同じ値）。これは窓だけ・rerank なしの想起（dsh の既定）での値。
6. 途中で見つけた不具合: capture の窓が 4 件目以降で空になる不具合は、並行して 790e13f で修正済み（修正前を再現すると、
   50 セッションで 0.883 → 0.700）。**2,048 トークンを超える窓が backfill を毎回止める不具合はまだ残っている**
   （5,000 セッションのストアで、起動時と 10 分ごとの backfill が毎回 HTTP 400 で失敗することを実測）。

## 何をどう測ったか

- **データ**: LongMemEval-S（`build/eval/memory/longmemeval-g1/longmemeval_s_cleaned.json`、G1/U2 と同じファイル）。
  一意なセッション 19,195 のうち、どの問題の根拠セッションでもない 18,255 を詰め物にした（固定 seed で並べ替え。
  5,000 件の内訳は模擬ユーザー 2,358 / ultrachat 1,406 / sharegpt 1,236）。規模 S のストアは先頭 S 件（入れ子）なので、
  規模の差は足された無関係セッションだけ。一意なセッションで足りたので、重複や日付ずらしは使っていない。
- **時系列**: 96 分おき（1 日 15 セッション）、最新が 2026/10/20。5,000 セッションで約 11 か月分。
- **設定**: dsh プラグインの既定（1 メッセージ 600 トークン、想起予算 2,048、updateLinks 有効、秘密情報の伏せ字あり、rerank なし）。
  事実抽出（LLM）はしていない（窓だけ）。
- **ストア**: 全メッセージを `capture()` で入れ（保存側のコストをここで測る）、`backfill()` で p2 窓を索引し、`VACUUM INTO` で詰めた。
  実ベクトルは EmbeddingGemma 300m（sidecar と同じ `HttpEmbedder`、32 件ずつ）で 57,509 窓を一度だけ埋め込み、規模ごとに使い回した。
- **性能**: 規模ごとに新しいプロセスで、両ホストの起動手順どおり「ストアを開く → backfill → 想起」の順に測った。想起は 100 問を 1 回ずつ。
  RSS は `process.memoryUsage()`、ピークは `resourceUsage().maxRSS`。実ベクトルの測定では、クエリを egemma-server で埋め込んだ。
  合成ベクトル（文字列から決まる乱数の 768 次元単位ベクトル）でも測った。総当たりの計算量は値に依らないので、実ベクトルと同じ時間になる
  （5,000 で計算部分 193 ms 対 184 ms）。10,000 セッションは合成ベクトルだけで測った。
- **精度**: 60 問（6 種類 × 10）の根拠セッションを、時系列の 5 % / 50 % / 95 % の位置（古い / 中間 / 最近）に植え、
  `Memory.retrieve` の結果に、LongMemEval が `has_answer` を付けた発言が入るかを数えた（LLM も judge も使わない、取り出し段階の指標）。
  規模 S は無関係セッションの数で、根拠（1〜6 セッション）はその上に足す。1 問ずつ SAVEPOINT で根拠を足して想起し、巻き戻す。
  この方式の結果は、最初から時系列順に作り直したストアの結果と、50 セッションで 180/180 一致した。

## どこで受け入れられなくなるか

基準: 1 回の想起が 1 秒を超える、または RSS が 2 GB を超える。ほかに、dsh の `recall.timeoutMs`（既定 4 秒）を超えると、その回の想起は黙って飛ばされる。

|線|現状のコード|修正案 1〜4 の後|
|---|---|---|
|RSS 2 GB|**約 7,000〜8,000 セッション（7〜8 万メッセージ）**|約 2 万セッション（10,000 で 0.99 GB）|
|起動直後の想起が 4 秒で打ち切り|約 12,000〜16,000 セッション|読み込みは 5,000 で 0.2 秒なので、10 万セッションを超えるまで届かない|
|想起 1 回 1 秒|約 2〜2.5 万セッション（p95）|10,000 で 47 ms なので、当面届かない|

毎日 15 セッションなら、7,000 セッションは約 1 年半。ただし効くのはセッション数ではなく**保存メッセージ数**なので、
dsh のセッションが LongMemEval（平均 10.3 メッセージ）より長ければ早く来る。dsh プラグインでは、RSS が dsh 本体のプロセスに上乗せされる
（Hermes の sidecar では単独のプロセス）。

## 最小の修正案（試作して測定、パッケージは変更していない）

`scripts/eval/scale/fix_prototype.mjs`。`Memory.retrieve` と**同じ結果**を返す（500・5,000・10,000、実ベクトルの 5,000 で 100 問すべて id が一致）。

1. **候補の発言だけ clip・lookup する**（効果が最も大きく、変更は `retrieve()` の数行）。`p.rawIds` と `versioned` が返した id についてだけ
   `asTurn` と除外判定をし、全メッセージ分は作らない。
2. **並べた索引を使い回す**: `indexUnits()` の結果と、ユニット集合ごとの連続した `Float32Array` 行列をキャッシュし、
   capture / backfill のたびに足す（`unitCache` と同じ寿命）。
3. **上位 100 を部分選択する**: 全スコアを並べ替える代わりに、大きさ 100 のヒープを使う（同点は index 順で、現行と同じ順位）。
4. **unit の本文をメモリに持たない**（retrieve は使わない）。読み込みでは本文を除き、行列へ直接流し込む（下表の lean）。
5. **backfill が何も索引しなかったときはキャッシュを捨てない**（10 分ごとの全件読み直しをなくす）。

|5,000 セッション|想起 p50|p95|RSS（100 回後）|GC 後ヒープ|ベクトル|
|---|---:|---:|---:|---:|---:|
|現状（実ベクトル）|209 ms|223 ms|1,450 MB|241 MB|151 MB|
|1〜4（実ベクトル、クエリ埋め込み込み）|**38 ms**|43 ms|**436 MB**|122 MB|151 MB|
|1〜3（合成）|24 ms|25 ms|883 MB|138 MB|151 MB|
|1〜4（合成）|24 ms|25 ms|553 MB|119 MB|151 MB|
|1〜4 + int8（合成）|24 ms|27 ms|290〜435 MB|114 MB|38 MB|

10,000 セッション（合成）では、1〜4 で 47 ms / 989 MB になる（現状は 384 ms / 2,805 MB）。int8 は JS では速くならず、メモリだけが 1/4 になる。
精度への影響は小さい（5,000 で答えの発言が入る割合は 0.517 → 0.500、60 問中 1 問が落ちた。結果の id が完全に同じ割合は 0.88）。
公開前に入れるなら、1・2・5 で効果の大半が取れる。int8 と近似索引は、2 万セッションを超える利用者が出てからで十分。

## 精度の変化

答えの発言（`has_answer`）が想起に入るかを数えた。60 問 × 3 つの古さ = 180 件。窓は修正後の capture と backfill で作った（両者は同一で、結果も 180/180 一致）。

|セッション|答えの発言を 1 つ以上|全根拠セッション|答えの発言の再現率|最初の答えの順位（中央値）|答え文字列が想起文に含まれる（短い答え 40 問）|
|---:|---:|---:|---:|---:|---:|
|50|0.883|0.683|0.768|3|0.675|
|500|0.717|0.517|0.597|3|0.650|
|2,000|0.667|0.450|0.546|5|0.625|
|5,000|0.517|0.383|0.444|7|0.600|

- 古さ別（古い / 中間 / 最近）の値は、すべての規模で完全に同じだった。順位付けは cosine と RRF だけで日付を使わず、古さが効くのは同点の並びと
  表示だけなので、**古さによる劣化は設計上起きない**。劣化は、足された無関係セッションの数による。
- 予算 2,048 トークンに入る発言は、1 回あたり約 8.5 件で規模によらない。最初の答えの順位が 3 → 7 に下がり、予算の端からこぼれる。
- 問題の種類別（50 → 5,000）: single-session-assistant 1.00 → 0.90、single-session-user 1.00 → 0.70、knowledge-update 0.70 → 0.50、
  temporal-reasoning 0.90 → 0.40、single-session-preference 0.90 → 0.30、multi-session 0.80 → 0.30。
- int8: 0.883 / 0.717 / 0.667 / 0.500（5,000 で 1 問だけ違う）。
- 修正前の capture の窓（790e13f より前を再現）: 0.700 / 0.683 / 0.583 / 0.500。50 セッションで 15 問を失っていた。

これは速さの問題ではないので今回の範囲外だが、長く使う利用者ほど想起が外れやすくなることは、公開時に把握しておくべき点。
評価済みの構成（事実抽出 + 必要時の rerank）や、予算を広げることで戻るかは測っていない。

## 途中で見つけた不具合

1. **capture() の窓が 4 件目以降で空になる（修正済み）。** 2f9c2a2 の `capture()` は 2 要素の配列を `windowUnitsP2` に渡していた。
   `windowUnitsP2` はセッション内の `pos` で配列を切るので、3 件目の窓は自分だけになり、4 件目以降は本文 `''`・ターンなしの窓になっていた
   （5,000 セッションで窓の 71.5 % が空）。並行して 790e13f（10/23 21:28）で修正され、backfill が本文の違う窓を作り直すようになったので、
   既存のストアも次の起動で直る。今回の実ベクトル測定は、すべて修正後のコードで行った。
2. **2,048 トークンを超える窓が backfill を止める（未修正）。** 1 メッセージを 600 推定トークンに clip しても、推定が実トークンより少なくなる文があり、
   5,000 セッションで 2 窓が egemma-server の上限を超えた（2,107 トークンと 3,085 トークン）。capture ではそのメッセージだけが失敗するが、
   backfill は 32 件のバッチごと失敗してループを抜ける。実測でも、5,000 セッションのストアでは起動時と 10 分ごとの backfill が毎回
   `HTTP 400 ... Input 0 has 2107 tokens` で失敗した。順番でその後ろにある未索引の窓（埋め込みサーバーが落ちていた間のメッセージなど）は、
   以後ずっと索引されない。修正案: 400 `context_length_exceeded` が返ったらバッチを分け、その窓だけ実トークンで切り詰めるか、飛ばして記録する。
3. **メッセージ id の衝突（小）。** dsh のメッセージ id は `sha256(session)` の先頭 8 桁 + 連番なので、別セッションと先頭 8 桁が重なると、
   capture の冪等判定でメッセージが黙って捨てられる。確率は 5,000 セッションで約 0.3 %、20,000 で約 4.5 %（10,000 では衝突なし）。
4. **segments 表に session の索引がない（小）。** capture のたびに表を全走査するので、保存側のコストが規模に比例して伸びる（0.2 → 0.55 ms）。

## 限界

- LongMemEval のセッションは英語で、平均 10.3 メッセージ。日本語や長いコーディングセッションでは、1 メッセージあたりの本文と clip のコストが変わる。
- 事実抽出（LLM）はしていない。事実ユニットが加わるとユニット数が増え、`factRows()` と `store.facts()` を毎回 SQLite から読むコストも加わる（今回は 0 件）。
- 精度は取り出し段階の指標で、回答の正誤ではない。rerank（`memory_search` の既定）も使っていない。
- RSS は V8 の GC の余白に左右される。数字は Node の既定のヒープ設定でのもの。
