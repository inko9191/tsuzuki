## 検索単位と返す原文

単位（埋め込んで順位を付けるもの）は、必ず原文の発言を返す。根拠として数えるのは、返した原文の発言だけ。

| 単位 | 埋め込む文 | 返す原文 |
|---|---|---|
| `t1` | 発言1件（ステージ1と同一で、キャッシュも共有） | その発言 |
| `c3` `c5` `c9` | 前後1/2/4発言の窓 | 窓内の全発言 |
| `p2` `p3` | 前1/2発言＋中心 | 窓内の全発言 |
| `x2` `x3` | 前1/2発言＋中心 | 中心の発言だけ |
| `rw` | Qwen による書き換え（代名詞・省略・相対日時を解消） | その発言 |
| `fact` | Qwen がセッションから抜き出した事実1文 | 引用した発言 |

- 窓はセッションをまたがない。返す原文は、中心、近い順（同じ距離なら前）の順。
- `+d` を付けた単位は、埋め込む文の先頭に `Date: <セッション日時>` を付ける。返す原文にも、セッションごとに1回だけ日時の行を付ける。
- `rw` と `fact` は、元の設定が日時付きなら `+d` になる。

## 検索・統合・後処理

- 検索対象は同じ会話内だけ。ベクトル検索は厳密なコサイン類似度で、同点は元の順序。
- 1つの（単位集合 × ランカー × クエリ文）ごとに上位100件を取り、RRF（k=60）で統合する。リストが1本だけならそのスコアのまま使う。
- BM25 は k1=1.2、b=0.75、会話ごとの IDF。前処理は NFKC → casefold → `\w+`。スコア0の単位は順位に入れない。
- 後処理は次の3通り。
  - `none`：何もしない
  - `cap3`：各セッション3件までを先に並べ、残りは元の順で後ろに回す
  - `mmr0.7`：関連度は統合スコアを min-max 正規化したもの、冗長度は単位ベクトルどうしのコサイン類似度
- 新しい発言を1件も返さない単位（重なった窓など）は、飛ばして k に数えない。

## 指標

各指標は、質問ごとの値の macro 平均。

- `recall@k`、`all_evidence@k`、`hit@k`（k = 5/10/20）：上位 k 単位が返した原文で数える。
- `recall@N10`：返した原文の最初の10発言で数える（発言数をそろえた比較）。
- `recall@T256`、`recall@T512`、`recall@T1024`：返した原文を順にトークン予算まで詰めた範囲で数える。入りきらない発言に当たったら、そこで止める。
- `payload_turns@10`、`payload_tokens@10`：上位10単位が返す原文の発言数とトークン数。
- トークン数は EmbeddingGemma 300m のトークナイザで数える（特殊トークンなし）。Qwen のトークン数とは一致しない。
- 95%CI は質問単位の対応ありブートストラップ（10000回、seed 0）。同じ会話の質問どうしの相関は考慮していない。

## ローカル Qwen による生成

- **入力**
  - 質問側（`para` `hyde` `decomp`）：開発用の質問文だけを渡す。
  - 文書側：会話本文だけを渡す。`rw` は同じセッションの直前6発言＋日時＋対象発言、`fact` はセッションの全発言（`[dia_id] 話者: 本文`）＋日時。
  - 正解・根拠・カテゴリ・検索結果は渡さない。再ランキングだけは、性質上、検索結果を見る。
  - 本番用の質問の生成はしない。
- **設定**：temperature 0、seed 0、`chat_template_kwargs.enable_thinking=false`、JSON スキーマで出力を拘束。`<think>` ブロックは取り除いてからパースする。プロンプトは `stages.json` に固定してある。
- **サーバーの同一性**：`freeze-generation` が、サーバーの model id とモデルファイル（GGUF）の SHA256 を `generation.json` に記録する。`generate` と `run` は、これと一致しなければ止まる。
- **失敗時の扱い**：パースできない出力は、次のように扱って失敗数を記録する。
  - `rw`：原文に戻す
  - `fact`：事実なし
  - 質問側：追加クエリなし
  - 再ランキング：元の順位のまま
- **キャッシュ**：生成物は `build/eval/memory/gen/<種類>.json`（gitignore 済み）に溜まり、中断しても続きから再開できる。採点時には、各項目のダイジェストが凍結した設定と一致するかを確認し、保存された返答を現在のパーサでパースし直す。
- **呼び出し回数**（開発用）：`rw` 5882回、`fact` はセッション数と同じ回数（数百回）、`para` `hyde` `decomp` は各1233回、再ランキング1233回。所要時間は Qwen の生成速度次第で、合計で数時間〜半日程度を見込む。

## 実行手順

```sh
.venv/bin/python -m unittest discover -s scripts/eval/tests -v
S=scripts/eval/locomo_memory_stages.py
.venv/bin/python $S register                 # stages.json はコミット済み（変更なしなら何もしない）
.venv/bin/python $S run --stage 2            # 窓（LLM なし、数分）
git add results/eval/memory/stage2-dev.* && git commit -m '...'   # 次のステージは、コミット済みの選択だけを読む
.venv/bin/python $S run --stage 2b           # BM25・統合・多様化（LLM なし）
# ここから Qwen が必要（127.0.0.1:8080 で起動しておく）
.venv/bin/python $S freeze-generation        # サーバーとモデル hash を固定 → generation.json をコミット
.venv/bin/python $S generate rw --limit 20   # 少数で出力を目視確認してから本番の生成へ
for k in rw fact para hyde decomp; do .venv/bin/python $S generate $k; done
.venv/bin/python $S run --stage 3            # 各ステージの結果をコミットしてから次へ
.venv/bin/python $S run --stage 4
.venv/bin/python $S run --stage 5            # 1233回の再ランキング
```

- サーバーが JSON スキーマを受け付けない場合は、`freeze-generation --no-json-schema` を使う。
- `/props` がモデルのパスを返さない場合は、`--model-path` で GGUF ファイルを指定する。
- `generate --workers N` は、llama-server の `--parallel` に合わせる。

結果は `results/eval/memory/stage<N>-dev.{json,md}` に出る。中身は集計値と設定、ハッシュだけで、本文は含まない。
質問ごとの行は `build/eval/memory/stage<N>-dev-rows.json` に出る。
開発用の評価は品質の比較だけが目的で、Qwen を止める必要はない。ただし、生成中は GPU を使うので、処理時間は性能値として扱わない。
