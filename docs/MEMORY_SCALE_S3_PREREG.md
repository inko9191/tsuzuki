# S3：事実の棚あり（設定 P）の想起を 5,000 セッションで（回答まで、事前登録）

状態：実行前に固定。計画 `results/eval/memory/s3-plan.json`（問題、コードのハッシュ）をコミットしてから回す。結果を見たあとで条件・判定は変えない。

## なぜ行うか

S2（`results/eval/memory/s2-report.md`）では、窓だけの想起を 5,000 セッションで改良する 4 案（予算 8,192、E2B の並べ直し 2 種、日付の絞り込み）のどれも、Gemma 4 E2B の答えを良くしなかった。50 セッションでも、想起に答えが入る割合 0.85 に対して正答率は 0.43 で、窓だけの記憶では読む側（E2B）が壁になっている。LLM を使わない改良の選別（SCR1、dev の問、探索）でも差は誤差の範囲だった。一方、事実の棚と更新のメモがある設定 P を E2B が読んだ E1 では、情報の更新が 0.90 だった（問題は別）。実際のインストール（Hermes、dsh の desktop プロファイル）も事実ありで動いている。**事実ありの設定 P は、5,000 セッションでも窓だけより E2B に良い答えをさせるか。** ユーザーの判断で J1-Q の再開より先に行う。

## 履歴と記憶づくり

- **詰め物**：規模試験の詰め物の先頭 5,000（参照用に 50）。dsh プラグインの `Memory` に入れ、区間を閉じて（`closeAll`）、プラグイン自身の事実抽出（`Memory.extract`）と更新の判定（`Memory.link`）を Gemma 4 E2B が行う（`scripts/eval/scale/s3_build.mjs`、`s3_build_run.py`）。抽出は 8 区間ずつ並行、更新の判定はすべての抽出のあと。判定はそれぞれ日付が前の区間の事実だけを読むので、日付順に 1 区間ずつ入れた場合と同じリンクになる。
- **質問ごと**：S2 と同じく詰め物（と区間）の日付をずらし、答えの会話を元の日付で入れる。答えの会話の事実と更新の判定は、プラグインの `drain()` で 1 区間ずつ行う（詰め物の事実が「前の事実」になる）。詰め物の事実の文は、日付をずらす前の日付で作られている（詰め物は答えに関係しない）。

## 問題

- **s2**：S2 の 60 問（主判定）。S2 で窓だけの 4 案の答えを見た問だが、設定 P はこの問で調整していない。
- **dev**：規模試験の 60 問（副）。

## 条件

- **A**：窓だけ、密な順、予算 2,048（S2 の A と同じ想起になるはず。一致を数えて報告する）。
- **P**：プラグインの想起（窓と事実を RRF、更新のメモ、予算 2,048。`rerank` なし）。
- 5,000 セッション（s2 と dev）と、参照の 50 セッション（s2 だけ）。

## 回答と採点

S2 と同じ。E2B（E1 のファイルとサーバー引数、窓 131072、1 スロット）、P の書式、U2 の Qwen judge。副次として Claude が 90 件の無作為抽出（seed 0）を、条件名を伏せて Qwen の採点を開く前に採点する（`scripts/eval/s3_claude_judge.py`）。

## 判定

- **主**：s2 の P-5000 − A-5000（60 問、質問単位の対応ありブートストラップ 10000 回、seed 0）。下限 > 0 → 改善。上限 < 0 → 悪化。それ以外 → 判定不能。
- **副（傾向）**：dev の P-5000 − A-5000、s2 の P-50 − A-50、P-5000 − P-50（事実ありでの規模の損失）、想起に答えが入った割合、事実と更新のメモの数、種類別。

## 限界

- 英語の LongMemEval。詰め物は別の人の会話を含むので、詰め物どうしの更新のリンクには意味のないものも混ざる（実際の利用では全部同じ人）。
- 事実抽出は 8 並行で行った（llama.cpp の並行処理で、1 つずつの場合と出力がわずかに違うことがある）。
- 60 問なので大きな差しか見えない。
