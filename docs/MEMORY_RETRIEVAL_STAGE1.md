# 外部記憶の検索評価（LLM による回答生成なし）

2026-10-12。最終的には小さい入力窓で Qwen の正答率を測るが、今回の段階では根拠発言の検索だけを評価する。
各ステージをコミットして報告後に止まる。push はしない。

## 現状と今回の範囲

v1 fp32 は ST と数値一致、v2 fp16 は LoCoMo の全入力で ST と一致確認済み。
prime-memory 0.22.1 の既定 ONNX q8 はプレフィックスと ST Dense 射影を使わない。
今回の既定は v1 fp32＋プレフィックス、比較は v2 fp16＋プレフィックス、参考は実物の prime ONNX worker。

引き継ぎ時の保留事項（fp32 既定化、bf16 分布、README 早見表）は別エージェントにより
`25707ce` にコミットされた。今回それらのコード・判定基準を変更しない。

このステージは分割と条件の固定、および発言1件ごとの**開発用**ベースラインまで。
本番用の実行コマンドはまだ実装しない。質問の言い換え・要約・回答生成は行わず、LLM は使わない。

## スコアを見る前に固定する条件

- データは既存の `datasets.json` にある LoCoMo `3eb6f2c585f5e1699204e3c3bdf7adc5c28cb376`。
  原本 SHA256 は `79fa87e90f04081343b8c8debecb80a9a6842b76a7aa537dc9fdf651ea698ff4`。
  正規化は既存 `fetch_data.py` と同じ1535問・5882発言。カテゴリ5、根拠なし・根拠IDが全て不明な質問は既存の除外を維持する。
  一部だけ不明な根拠IDを持つ質問は既存と同じく既知のIDだけを分母にする。該当は開発用4問、本番用0問で、分割 manifest に記録。
- 分割は質問単位、会話×カテゴリで約80%開発用／20%本番用。
  seed は `egemma-memory-stage1-2026-10-12`。質問IDの SHA256 による固定順で、各層の本番用件数を四捨五入する。
  NFKC・casefold・句読点除去・空白統一後の同一質問は会話内で束ね、束単位で分割する。
  カテゴリが異なる同一質問も分離せず、最小カテゴリの層に置く。1束しかない層は開発用。
  この処理は機械的に全質問を分割するが、本番用の本文・正解を調整や分析には使わない。
- 本番用は `build/eval/memory/holdout.json` に隔離する。通常の評価は `dev.json` と共通 `corpus.json` だけを読む。
  分割ファイルとルールの SHA256 を公開メタデータ `results/eval/memory/split.json` に固定し、上書き・変更を拒否する。
- 埋め込みは768次元。v1 fp32 / v2 fp16 を明示し、クエリ `task: search result | query: `、
  文書 `title: none | text: ` を付ける。エンジンは2048トークンで切る。prime は prefix なし、5000文字上限、q8 CPU。
  各経路の切り詰め件数を記録する。今回は短い発言中心なので上限の差による影響も件数で確認する。
- 文書は既存と同じ `speaker: text` に画像の BLIP caption があれば追記する。日時は検索本文に入れない。
  会話内の発言だけを候補とし、正規化ベクトルの内積で厳密検索。tie は corpus の元の順序。
- 根拠 Recall@5/10/20 は `上位k件の中の正解根拠発言数 / その質問の正解根拠発言数`。
  質問単位の macro 平均を報告する。補助指標は全根拠回収率 All、1根拠以上回収率 Hit。
- 質問の代理分類はカテゴリ2なら時系列、それ以外でカテゴリ1または根拠2件以上なら複数箇所、残りなら単一事実。
  これは公式ラベルと根拠数による便宜的な分類で、カテゴリ3（open-domain）も単一事実側に入り得る。
  元カテゴリ1/2/3/4の集計も必ず残す。公式コードのカテゴリ1は multi-hop、カテゴリ2/3/4は temporal/open-domain/single-hop の群：
  [LoCoMo 評価コード（固定版）](https://github.com/snap-research/locomo/blob/3eb6f2c585f5e1699204e3c3bdf7adc5c28cb376/task_eval/evaluation.py)。
- 新しい cache 名前空間を使い、過去の全質問ベクトルや per-query 結果を読み込まない。
  cache は入力、ルール、モデル重み、トークナイザ、実行コードの hash で識別する。

**既存評価との重複**：LoCoMo 全1535問は今回より前に公開ベンチマークで評価済み。
従って「本番用」はこれからの設定調整に対する holdout であり、過去も含めた完全な未使用テストではない。
同一会話を両分割で検索するため、会話をまたぐ汎化性能も測っていない。近い言い換えや同じ根拠を持つ別質問は残り得る。

2026-10-12のレビュー後の[分割・推論の判断](MEMORY_RETRIEVAL_SPLIT_DECISION.md)で、現行分割を維持する(b)を採用した。
以降は会話単位の区間と会話ごとの符号検定を併記し、同じ10会話内の未調整質問への性能として報告する。

選択順は開発用の macro Recall@10、同点なら平均 payload トークン数@10 の少ないもの、なお同点なら設定IDの辞書順。
窓や要約は上位k件に含む原文の和集合で根拠を数え、同じ根拠の重複は1件とする。
要約の出典セッション全体を無条件に回収済みとして数えない。実際に返す原文だけを回収済みとする。
大きい窓では同じkでも返す原文が増えるので、payload量と同一発言予算でのRecallも並べる。
Recallだけで小さいLLM窓での正答率を断言しない。固定グリッドを結果に合わせて増やさない。

生成モデルの選定はローカルで利用可能なものを確認した時点で行い、生成・検索スコアを見る前に別の設定ファイルで固定する。
質問の言い換え生成には質問だけを渡し、正解・根拠・検索結果を渡さない。要約生成には原文だけを渡し、QA注釈を渡さない。
データに添付された既存要約・event_summary・observation は生成物の由来が異なるので使わない。
本番用の生成物は設定選択後にだけ作る。

## 取りこぼしの分析

v1 の開発用 Recall@10 が1未満の質問をすべてローカル audit queue に保存する。
最初の手動点検は seed＋`audit`＋質問IDの SHA256 順で20問。結果を見て例を選び直さない。
複数ラベルを許す：言い換え、時間表現、複数箇所、断片の切れ目。原文確認で原因を断定できなければ「その他／不明」。
根拠数や公式カテゴリだけで原因を自動断定しない。単一発言のステージ1では隣接発言を欠く境界の問題も点検する。
公開レポートはIDと自分の分析文・集計だけにし、質問・本文・正解の引用はコミットしない。
最終設定では全取りこぼしをこの方式で分類する。今回の20問は全体の原因分布を推定する標本ではない。

## 実行と検証

```sh
.venv/bin/python -m unittest discover -s scripts/eval/tests -v
.venv/bin/python scripts/eval/locomo_memory.py prepare  # 一度だけ、計測前に split をコミット
.venv/bin/python scripts/eval/locomo_memory.py run      # dev の3経路を直列に実行
```

追加依存なし。既存のデーモン起動・ONNX worker・原子JSON保存を使う。
ベクトルが有限・768次元・単位長であることをスコア計算前に検査する。デーモンは必ず finally で停止する。
本文・rankings・audit queue・ベクトルは `build/eval/memory/`、本文なしの集計とhashは `results/eval/memory/`。
LoCoMo は CC BY-NC のためデータファイルをコミットしない。

開発用は品質だけを比較するため、待機中の Qwen サーバーは止めず前後の状態を記録する。単独性能の測定値にはしない。
本番用ではユーザー指示に従い Qwen・ComfyUI・Ollama 等の GPU 負荷を停止し、
`scripts/gpu_quiet_check.sh` の成功と停止前後のプロセス・ポート・GPU状態を記録してから実行する。
他エージェントの GPU 試験と並行に走らせない。
