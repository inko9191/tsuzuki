## G2候補と限界

1. **LongMemEvalの固定した別質問を日本語化**。G1と重ならないIDを種類ラベルだけでseed抽出、履歴/質問/正解/rubricを同じ翻訳器・版で一度翻訳し、独立した二言語確認者が固有名詞・日付・更新・否定を確認する。翻訳は回答生成より前にhash固定、出来の良い例への差替えなし。元配布MITと由来を保持し本文はignored。履歴全体の翻訳には数百万tokenが必要で、翻訳器と利用料金が未指定なので所要時間/費用は未確認。元の合成/編成履歴と翻訳品質の影響が混ざり、日本語の自然な長期会話を検証しない。
2. **LoCoMoの日本語化**。取り込み済みの英語raw/factをそのまま日本語索引へ使わず、翻訳rawから凍結英語fact promptで一度取り込む。元LoCoMoは設計に使用済みなので、未知会話一般化の証拠にはならず、同じ内容の言語変更の探索だけ。元配布の利用条件・翻訳データの公開可否を実行対象revisionで確認する。既存取り込み単価の移植は推定で、日本語token数/生成時間は未測定。
3. **独立した日本語の長期対話**。現時点で利用許可・長さ・正解要素・時系列/更新/棄権を備えた手元のデータは未確認。ユーザーから利用を許可された匿名会話が候補。質問と必要要素は条件別回答を見る前に作成し、取り込みの上限/評価問い/比較を登録する。私的内容を勝手に外部送信しない。長期記憶問題のある公開日本語データの具体的な出典・license調査はG2指定後に行う。通常のQA/短い対話集合を長期会話の代用品とは呼ばない。

どの案でもC-final-norwの英語prompt/パラメータを変えず日本語入力から英語の短い回答を出す。翻訳・名前表記・英語出力評価の偏りを記録し、日本語goldへ英語tokenF1だけを直接当てて意味精度としない。A/B/C同じ質問、host-cache-off、8k C/128k Aの厳密preflight、1並列、独立意味judgeと盲検人間確認を実行前に確定する。256kや日本語用チューニングへ自動移行しない。

## G3：G1出力の盲検確認

- 全30問を対象にする（抽出追加なし）。C−Aが異なる質問を先にし、残りseed `longmemeval-g3-v1`のID hash順。差が出た例だけを全体性能としない。
- 自動採点前に固定した公式category rubricを人間へ渡す。質問・gold・必要なら原履歴の根拠で確認する。temporal off-by-one許容/preferenceの全rubric不要というLLMの操作的基準を別記し、「完全な必要要素全正答」と混同しない。
- 1問につきA/B/C回答を匿名X/Y/Zにし、質問ごとの匿名割当と提示順を別seedで固定、対応表を別privateファイルへ。条件名/F1/時間/メモリ/検索順位は盲検版へ出さない。回答文から条件を推測できる可能性は残る。
- 最初の人間評価版ではLLMラベルを隠す。人間がyes/no/判定不能・不足/誤り要素・矛盾・根拠を保存した後に、依頼された質問/正解/全条件回答/LLMラベル一覧の照合版を開く。人間の判断でG1の主LLMラベルを上書きしない。別表で一致率・偽yes/偽no・種類別誤りを報告。
- 必須意味要素の一般尺度を別途実行するなら、モデル回答を見ない作成者が人物/行為/対象/時点/更新値/全必要部品を分解し、許容表現と禁止矛盾を先にhash固定する。要素1/0、全必須要素1かつ矛盾なしを主尺度にする。G1を見た後にこの尺度へ主結果を差替えない。
- 所要は30問×3回答×2〜4分=3〜6人時（推定）、履歴確認/必要要素表作成は別。1人評価には裁定者間の信頼性がなく、二人確認なら概ね6〜12人時＋裁定。担当者はユーザー、実施はユーザー判断を待つ。
- 出力はprivate review.json / blinded-review.html / review-key.json。公開は件数・一致/誤り集計・hashのみ。チャットへ個々の会話本文を自動掲載しない。
